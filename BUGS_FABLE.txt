FABLE-01  ltrim/rtrim/trim send trim-string args in the wrong order
  File: lib/spark_ex/functions.ex:719, 737, 755 (ltrim/rtrim/trim with trim_string)
  When a trim character set is given, spark_ex builds
  {:fn, "ltrim", [to_expr(col), to_expr(trim_string)]} i.e. (src, trim).
  PySpark sends the trim string FIRST: _invoke_function_over_columns("ltrim",
  trim, col) (connect/functions/builtin.py:2468-2492), because Spark's SQL
  form is ltrim(trimStr, srcStr) (catalyst StringTrimLeft 2-arg constructor,
  stringExpressions.scala:1561). Result: silently wrong output — characters of
  `col` are trimmed from `trim_string` instead of the other way around.
  btrim/2 (functions.ex:773) is correct; only ltrim/rtrim/trim are swapped.

FABLE-02  mask/2 with partial options sends NULL for omitted chars, leaving
          text unmasked (privacy-sensitive)
  File: lib/spark_ex/macros/function_registry.ex:216-218 (mask entry) with
        lib/spark_ex/macros/function_gen.ex:283-315 ({:col_opt} codegen)
  PySpark always sends 5 args, substituting defaults lit("X"), lit("x"),
  lit("n"), lit(None) for omitted upper/lower/digit/other chars
  (builtin.py:3092-3106). The {:col_opt, [upper_char: nil, ...]} generator
  drops only TRAILING nils and encodes interior nils as lit(nil). So
  mask(col, digit_char: "0") sends mask(col, NULL, NULL, '0'); in Spark's
  mask a NULL char means "retain the original character", so upper/lowercase
  letters pass through unmasked instead of becoming X/x. The registry defaults
  should be "X"/"x"/"n"/nil like PySpark.

FABLE-03  await_termination with no timeout crashes the Session GenServer
  File: lib/spark_ex/internal/streaming_timeout.ex:21-23, with
        lib/spark_ex/streaming_query.ex:112 and
        lib/spark_ex/streaming_query_manager.ex:77, via
        lib/spark_ex/connect/client.ex:566 and :2203
  StreamingTimeout.resolve/1 writes Keyword.put(opts, :timeout, nil); in
  run_execute_plan, Keyword.get(opts, :timeout, 60_000) then returns the
  literal nil (key present), and Stub.execute_plan(channel, request,
  timeout: nil) reaches gun's `receive ... after nil`, which raises
  :timeout_value — inside the Session GenServer handle_call, killing the

  and returns None (connect/streaming/query.py:94-98). nil must be mapped to
  :infinity at the gRPC layer (Session.call_timeout already handles the
  GenServer side). Note: even when fixed, the blocking call occupies the
  session process, so StreamingQuery.stop/1 on the same session cannot

-- Plan/expression encoding ----------------------------------------------------

FABLE-07  Window frame boundary 0 not normalized to CURRENT ROW — RANGE
          frames diverge
  File: lib/spark_ex/connect/plan_encoder.ex:3539-3560 (and window_spec.ex
        never converts 0)
  PySpark maps boundary 0 to current_row = True for both ROW and RANGE frames
  (connect/expressions.py:1151-1153, 1190-1192). spark_ex encodes 0 as a value
  literal (long for range). For RANGE frames a long-literal boundary requires
  a single numeric order column in Catalyst, so range_between(0,
  :unbounded_following) over a timestamp or multi-column ordering fails
  analysis on the server while the identical PySpark call works.

FABLE-08  rewrite_expr/4 misses the 4-tuple {:alias, expr, name, metadata} —
          subquery/cross-DF references under a metadata alias are not hoisted
  File: lib/spark_ex/connect/plan_encoder.ex:2661-2664 (only the 3-tuple alias
        is matched; 4-tuple falls into the catch-all at :2746)
  Column.alias_/3 with metadata: produces {:alias, expr, name, metadata_json}
  (column.ex:434). Because rewrite_expr returns the 4-tuple unchanged, a
  subquery expression (exists/scalar) or cross-DataFrame column reference
  nested under a metadata alias is never collected into
  with_relations.references — the plan's subquery_expression.plan_id points at
  a relation missing from the proto tree (server-side "plan not found"). The
  same expression without metadata works; with_columns' rewrite_alias/4
  (plan_encoder.ex:2559) handles the 4-tuple correctly. PySpark collects
  references through aliases regardless of metadata (plan.py:162-177, 601-607;
  expressions.py:223-225).

FABLE-09  select(df, ["*"]) and dict-agg %{"*" => "count"} fail: raw-string
          paths bypass the star special case
  Files: lib/spark_ex/data_frame.ex:2535 (normalize_column_expr/1),
         lib/spark_ex/grouped_data.ex:120-128 (pairs_to_columns/1)
  PySpark converts string columns through F.col(), which maps "*" to
  UnresolvedStar (connect/functions/builtin.py:250-258); df.select("*") and
  df.agg({"*": "count"}) work. SparkEx.Functions.col/1 has the same special
  case, but normalize_column_expr(name) and pairs_to_columns build {:col, "*"}
  directly, which the encoder emits as UnresolvedAttribute{unparsed_identifier:
  "*"} (plan_encoder.ex:1438) — the server raises UNRESOLVED_COLUMN. Route raw
  strings through the same star/"x.*" handling as col/1.

-- gRPC client -----------------------------------------------------------------

FABLE-10  Server RetryInfo.retry_delay REPLACES exponential backoff instead of
          flooring it
  File: lib/spark_ex/connect/client.ex:2526-2529 (backoff_with_retry_info/3)
  The helper returns min(retry_delay_ms, max_server_retry_delay) as the entire
  sleep, discarding attempt-based exponential backoff and jitter. PySpark
  computes wait = max(exponential_wait, min(retry_delay, max_server_retry_delay))
  plus jitter (client/retries.py:157-167) — the server hint is a lower bound,
  never a reduction. A server attaching a small retry_delay (10-100 ms) to a
  persistent error makes this client hammer it 15 times at a fixed short
  interval where PySpark backs off 50ms → ... → 60s. Also affects the reattach
  path (client.ex:1716).

FABLE-11  Reattach retry budget never resets on progress
  File: lib/spark_ex/connect/client.ex:1565-1578 (with :1673-1694)
  On a successfully received response only empty_eof_streak is reset;
  state.attempt persists for the stream's lifetime. PySpark constructs a fresh
  Retrying per consumed response (reattach.py:159, core.py:789-790), so the
  15-retry budget applies per fetch. A long-lived reattachable stream (e.g.
  the listener-bus event stream) that survives >15 transient blips in total
  over hours fails with :reattach_incomplete_result, and each new blip's
  backoff starts from the lifetime counter (pinned at 60 s) instead of 50 ms.

FABLE-12  URI.decode_www_form corrupts '+' in connection-string parameters
  File: lib/spark_ex/connect/channel.ex:309-310 (parse_params)
  Both key and value are decoded with URI.decode_www_form/1, which turns '+'
  into a space. PySpark uses urllib.parse.unquote on the value only
  (client/core.py:409), leaving '+' intact. sc://...;token=abc+def yields
  token "abc def" here (auth failure) vs "abc+def" in PySpark; any param value
  with a literal '+' diverges. Use percent-decoding without plus-to-space.

FABLE-13  TIMESTAMP mapped to deprecated {:datetime, :microsecond}, collapsing
          into TIMESTAMP_NTZ
  File: lib/spark_ex/connect/type_mapper.ex:104

  {:naive_datetime, :microsecond} with a Logger.warning per use

FABLE-25  process_all_available/1 has a ~65 s effective deadline; PySpark
          blocks indefinitely
  File: lib/spark_ex/streaming_query.ex:134-139
  No :timeout is passed, so the command runs with the 60 s default gRPC
  timeout (client.ex:566) and a 65 s GenServer call timeout
  (session.ex:3262-3270). The server sends nothing until the drain completes,
  so any processAllAvailable taking longer makes the caller exit with a raw
  GenServer :timeout (DEADLINE_EXCEEDED is terminal, client.ex:2444-2449, so
  reattach can't save it). PySpark blocks with no client deadline
  (connect/streaming/query.py:134-139) and Spark documents the call as
  potentially blocking for extended periods.

FABLE-26  Listener-bus DOWN handler races stream restart → leaked server-side
          listener and reader process
  File: lib/spark_ex/streaming_query_listener_bus.ex:357-359
  The {:DOWN, ..., :shutdown} clause for closing_stream?: true doesn't check
  the dead pid is the CURRENT stream_task. Sequence: remove last listener
  (kills task1, sets stream_task: nil, closing_stream?: true) → add_listener

  stream_task == nil (line 276) and skips stop_event_stream — the server-side
  listener and task2's gRPC stream leak forever. PySpark joins the single
  handler thread under a lock (connect/streaming/query.py:312-345).

FABLE-27  ManagedStream controller processes are never stopped — one leaked

  File: lib/spark_ex/managed_stream.ex:135-143 (do_close/2)

FABLE-33  Decimal literals with positive exponent encode in scientific

  File: lib/spark_ex/connect/client.ex:1542, :1709-1735
  PySpark reattaches immediately and indefinitely on graceful EOF
  (reattach.py:175-188; no sleep, no budget). spark_ex sleeps before every
  graceful-EOF reattach and after 3 zero-progress EOFs charges each further
  EOF against the 15-attempt budget, surfacing :reattach_incomplete_result
  after ~19 silent cycles. Deliberate anti-spin guard per comments, but a real
  divergence: a legitimate long-running query producing no responses for an
  extended period fails here and completes in PySpark.

FABLE-39  checkpoint/local_checkpoint silently return the un-checkpointed

  File: lib/spark_ex/data_frame.ex:1750, :1790, :1851-1856

  succeeded. PySpark surfaces the server error. Callers can't distinguish a

FABLE-40  NA.drop/2 skips :how validation when :thresh is provided
  File: lib/spark_ex/data_frame/na.ex:129-146

FABLE-41  sample/4 rejects fraction > 1.0 without replacement; PySpark accepts
  File: lib/spark_ex/data_frame.ex:2662-2675 (validate_sample_fraction!/2)
  PySpark performs no client-side range check and Scala Dataset.sample only
  requires fraction >= 0; df.sample(1.5) is valid (over-sampling caps at all

FABLE-42  {name, alias} tuple form accepted but the alias silently discarded
  File: lib/spark_ex/data_frame.ex:2537-2538 (normalize_column_expr)

FABLE-43  Writer partition_by call-time option rejects a bare string

FABLE-44  CSV :sep/:separator value not coerced to string like sibling options

- Cross-cutting theme 1: validation/decoding errors raised inside the Session
  GenServer (FABLE-03, -04, -05, -06) take down the whole session including
  the server-side release; client-side input errors should return
  {:error, ...} like the existing safe_encode path.
- Cross-cutting theme 2: app-lifetime ETS tables without cleanup
  (FABLE-29, -52, -53) and process leaks (FABLE-26, -27) make the client
  unsuitable for long-lived nodes without periodic restarts.
- Cross-cutting theme 3: GenServer.server() is accepted by specs but only raw
  pids work in several places (FABLE-31, -45).

  WriterV2 and MergeIntoWriter proto construction, catalog plan mapping,
